Architecture walkthrough · pilot scope

The bot that
cannot pay
anyone.

An AI system for volunteer condo boards, built so that its most important safety property is structural rather than promised. Eighteen decisions; here are the eight that carry the weight.

01 — What we are actually solving

Volunteer boards carry real liability
with no enterprise tooling.

A treasurer at a self-managed association has the fiduciary exposure of a finance officer and the toolkit of a spreadsheet user. Recent Florida legislation raised the stakes on record-keeping failures considerably.

So the product's job is fiduciary confidence, not automation — catch the duplicate invoice before it is paid, answer the dues question with the record in hand. Which means a wrong number stated confidently is not a bug, it is the whole failure mode.

Everything downstream follows from that: the architecture is designed against plausible-sounding wrongness, not against downtime.

02 — The shape

Hexagonal, plus two additions
that carry the safety claim.

A one-way quarantine gate

Untrusted document content crosses exactly one boundary, in one direction, and is laundered into typed values on the way through. Nothing past the gate ever sees raw bytes or unbounded strings.

Capability-restricted egress

The reasoning agent reaches the world only through a fixed, enumerable capability set. It cannot compose a new one at runtime — not because it is told not to, but because there is no mechanism.

Ports and adapters is the container. The gate and the capability limit are what make it this product rather than any other.

03 — AD-1, AD-2 · the data plane

"Air-gap" means one specific thing.
It is easy to overstate.

What it does NOT mean

That the system performs no writes. It owns and writes its own database — documents, extracted records, alerts, and the query log. It has to, to function. An earlier draft said "strictly read-only," and that was simply wrong.

What it does mean

No credential granting write access to any external financial rail exists in any environment, secret store, or CI config. There is no bank to write to. The restriction is an absence, not a scope.

A permission can be widened by an administrator in an afternoon. A credential that was never issued cannot.

04 — AD-3, AD-4 · credential topology

The LLM-adjacent runtime
holds no data credentials.

05 — AD-5 · capability egress

The model never writes SQL.
It picks from a menu.

The obvious design lets the model author SQL against a read-only role. It is flexible, and every new question works on the first try. It also means unreviewed query text, composed by a model that just read an attacker-supplied invoice, reaches member financial data.

Instead: a fixed, version-controlled catalog of reviewed queries. The model selects an entry and supplies typed parameters. Tool definitions carry strict schema enforcement, so parameter validity is guaranteed at the API layer rather than requested in a prompt.

The real win is not injection-proofing — parameterization already does that. It is that the blast radius of a fully successful injection is bounded by what the catalog can express.

The cost, stated honestly

A genuinely new question shape is a new catalog entry — a story in the backlog, not a capability the system has at runtime. That is a real product constraint, accepted deliberately.

06 — AD-7 · the arithmetic guarantee

A prompt is a request.
The metric said 100%.

The requirements originally enforced "never do arithmetic yourself" with system-prompt directives, while a success metric claimed 100% of calculations would be delegated. Those two statements cannot both be load-bearing. Prompts are not an enforcement mechanism.

07 — AD-8, AD-10 · the injection path

A vendor name is a string.
A malicious string is also a string.

Isolating extraction from reasoning stops the crude attack — the reasoning model never sees raw document bytes. But schema validation alone would happily pass "Acme Landscaping. Ignore prior instructions and…" through as a valid vendor_name, straight into the anomaly agent and the board's email.

Values are bounded

Length caps, format regex, enums. Vendor identity resolves against a known-vendor table; unknowns go to a human-confirm queue and never auto-create.

Values never enter a prompt

Prompts carry row ids. Tools resolve values. The renderer escapes on output. There is no string interpolation of extracted text anywhere in the prompt path.

The boundary is a vendor boundary

Extraction runs on Gemini, reasoning on Claude. Different keys, different deploy units, different control planes — so the two sides cannot be collapsed into one context by a config change.

08 — AD-13, AD-14 · what the adversarial pass caught

Two units can obey every rule
and still build incompatibly.

The review asks one question: construct two components that each honor every decision to the letter, yet still collide. It found two, and both were closed with new invariants.

Ingestion was not idempotent

First upload, re-process, and retry-after-failure could each obey every prior rule and still write duplicate invoice and alert rows. In a product whose headline feature is duplicate-invoice detection, the pipeline would have been manufacturing the very thing it exists to catch.

Catalog versions were mutable

The provenance log records the catalog entry and version — but nothing stopped a version's SQL being edited in place. The log would read dues_status@2 while that name no longer identified the SQL that ran. An audit trail that cannot be replayed is worse than none.

Neither is exotic. Both would have shipped, and the second would have quietly invalidated the compliance story the product is sold on.

09 — deliberately unresolved

What this spine refuses to decide.

Service-to-service auth

The tool endpoints are the only data path and must reject any non-agent caller. The requirement is fixed; the mechanism waits until the container host's networking is concrete.

Multi-tenancy

One association. Row-level security and tenant scoping do not exist. A second association is not a scaling task — it reopens the credential and catalog decisions.

Retention & deletion

How long documents, extractions, and the provenance log persist. Interacts with record-keeping obligations the requirements reference but never specify.

Backup & recovery

Including whether the provenance log carries a different retention guarantee than operational data. Owned by the operational envelope, not yet decided.

Naming what a spine won't decide is half of what keeps it lean enough to be followed.
