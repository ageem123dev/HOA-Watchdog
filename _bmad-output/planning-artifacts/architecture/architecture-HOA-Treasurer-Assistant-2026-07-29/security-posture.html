What this document is for01

This records the controls the Watchdog's architecture actually enforces, the mechanism behind each one, and what a reviewer could inspect to confirm it. It is written to be checked, not to reassure — every claim below either names a structural property or is marked as something weaker.

Controls are typed. A structural control cannot be violated without changing the architecture. An enforced control is checked at runtime and fails closed. A procedural control depends on people following it, and should be read with appropriate skepticism.

AD-4 Enforced Two database roles. watchdog_writer is used only by ingestion; watchdog_reader is SELECT-only and is the only role a model-initiated query executes under. Postgres GRANT statements; a negative test asserting the reader role's INSERT fails.
AD-5 Structural The model never authors SQL. It selects a reviewed catalog entry and supplies typed parameters, validated at the API layer via strict tool use. Tool definitions carry strict: true and additionalProperties: false; the catalog is version-controlled and reviewable as ordinary code.
AD-7 Enforced Every numeric token in a rendered answer must appear in that turn's tool result set. Unreferenced numerals are rejected pre-render and the turn retries. Validator unit tests, including the negative case: a fabricated figure must fail. This is what makes the 100% delegation metric assertable.
AD-8 Structural Extracted strings are never interpolated into a prompt. Prompts carry row identifiers; tools resolve values; the renderer escapes on output. Prompt-assembly code contains no interpolation of extraction output. Vendor identity resolves against a table, never a free string.
AD-9 Enforced Extraction is invoked with a machine-enforced output schema. Schema-invalid output halts the pipeline; no partial extraction proceeds. The extractor call sets responseSchema; the halt path returns a structured error rather than a best-effort record.
AD-10 Structural Extraction and reasoning are different vendors, different keys, different deploy units. Raw bytes and raw extracted text never enter the reasoning context. Two provider SDKs, two credentials, no shared client. The trust boundary is a vendor boundary and cannot be collapsed by configuration.
AD-12 Enforced Each query execution appends user, timestamp, catalog entry and version, bound parameters, and exact SQL — before returning results. Append-only. No application role holds UPDATE or DELETE on the log table; a query path that bypasses the write is a failing test.
AD-14 Enforced A catalog entry version, once used in production, is frozen. Changing SQL or the parameter schema mints a new version. CI diff check on published catalog versions. Without this the audit trail cannot be replayed and AD-12's records become unverifiable.

The injection path, specifically03

The realistic attack is not someone breaking into the database. It is a vendor sending an invoice whose text is written to be read by a language model — a description field containing instructions rather than a description. The document arrives through the association's own front door, looking exactly like the documents the system exists to process.

Isolating extraction from reasoning (the dual-LLM pattern) blocks the crude version of this: the reasoning model never sees the raw document. But schema validation alone would not stop a payload that fits the schema — vendor_name is a string, and a malicious string is still a string. Three controls compound against that:

Values are bounded, never interpolated into prompts, and the model's entire capability surface is a fixed list of reviewed queries. A successful injection would still be talking to something that can only ask permitted questions.

That is the substantive point about the query catalog. Its value is not primarily SQL-injection prevention — parameterization handles that. It is that the blast radius of a fully successful prompt injection is bounded by what the catalog can express, and the catalog is a reviewed, version-controlled artifact rather than something the model composes at runtime.

What this posture does not cover04

Stating these plainly is part of the diligence claim. A control register that lists only strengths is not evidence of anything.

Extraction accuracy is not a security control

Schema conformance guarantees shape, not truth. A misread amount produces a well-formed, confidently-presented wrong figure. Nothing in this register detects that; it is a model-quality problem addressed by review, not by architecture.

Garbage in, audited garbage out

Under the uploads-only data plane the system's view of reality is whatever the board uploaded. It cannot detect an invoice that was never uploaded, and a complete-looking answer may rest on incomplete records.

Third-party data residency

Association financial records reside on managed cloud infrastructure and are processed by two external model providers. That is a deliberate trade-off for a pilot, not an oversight — but it is a real one and belongs in any disclosure to the board.

No multi-tenant isolation yet

The pilot is a single association. Row-level security and tenant scoping in the catalog do not exist. Onboarding a second association without revisiting AD-4 and AD-5 would be a serious defect, not a scaling task.

Retention and deletion are undecided

How long documents, extractions, and the provenance log persist is unresolved, and interacts with record-keeping obligations the product's requirements reference but do not specify.

Open before pilot05

Unresolved — required before handling real association data

These are gaps in the current architecture, not deferred niceties:

  • Service-to-service authentication on the gateway's tool endpoints. Those endpoints are the only data path in the system; the requirement is fixed, the mechanism (mTLS, signed service token, private networking) is not yet chosen.
  • Backup and recovery posture for the Watchdog store, including whether the provenance log has a separate retention guarantee from the operational data.
  • Retention and deletion policy, per the limitation above.

Standing of this document06

This is a description of an architecture, produced during design and before implementation. It is not an audit, not a penetration-test result, and not a legal opinion about any board's obligations. Controls marked structural or enforced describe what the architecture requires; confirming that the built system matches is the job of implementation review and testing, which have not yet happened.
