## The epic's signature defect

Measured across all twelve story files:

| Phrase | Story files containing it |
| --- | --- |
| `silently` | **12 of 12** |
| `guard that` | 10 of 12 |
| `vacuous` | 8 of 12 |
| `expired` | 4 of 12 |

Nearly every defect this epic found was one shape: **something that passes by not doing its job.**
A partial catalogue, all real:

- A bare `rejects.toThrow()` that also passed when the table was absent.
- A loop that asserted over an empty list.
- A `Promise.all` "concurrency" test that passed against a deliberately racy implementation.
- A `requestTimeout` that only logged a warning.
- A migration-text test that matched the migration's own comment rather than its SQL — **twice**, in
  two different stories.
- A CI path filter that failed open three times in three rounds (`.env*`, then `.github/`,
  `.claude/`, `_bmad/`).
- A deny-list of forbidden port methods that let `archive()` and `storage_key` through.
- A test file git classified as **binary** — two literal NULs used as a glob sentinel — so no
  reviewer, human or otherwise, could read the diff.
- A control test for preselection that queried an HTML attribute React never sets, so adding
  `autoFocus` passed it.
- A `vitest` include glob that excluded `.tsx`, so the first component test would have passed **by
  never running**.
- A dashboard link test that compared the rendered `href` against the same constant that built it.

**The lesson is not "write better tests."** It is that this class is invisible to the person who
wrote it, and only two instruments find it: the **sensitivity check** (break the code, watch the test
fail) and an **adversarial reviewer**. Each is blind to what the other sees. Mutation testing only
probes where a test already exists; review asks what was never considered.

## What went well

**1. The review pipeline changed measurably, mid-epic.**

| Story | MR review rounds |
| --- | --- |
| 1.5d | 5 |
| 1.6b | **8** |
| 1.6c | **1** |
| 1.6d | **1** |

Story 1.6b's eight rounds and roughly eleven pushes was the trigger. Moving the first CodeRabbit
round into the IDE — before the merge request exists — took the MR round count to one and held it
there for two stories. Every round removed is a push, a pipeline and a wait.

**2. CI cost came down without weakening a gate.** Duplicate pipelines were about half the bill and
cost nothing to remove. Two *other* attempts at making CI cheaper were wrong in ways that looked
right, and both were caught: dropping `npm test` left no gate at all, and running the full suite only
on `main` was post-merge detection, because `CI_COMMIT_BRANCH` is unset in merge-request pipelines.

**3. Decisions were recorded where they would be read.** Migration comments explain why a constraint
has the shape it has; port headers explain why a method is absent. Story 1.6d's write port exists
because `quarantine-queue.ts` said in its own header that it should.

**4. The architecture survived contact.** No AD was weakened to make a story land.

## What did not go well

**1. The gates disagreed about what "green" means — for three consecutive stories.** `npm run build`
and `eslint` passed while `tsc --noEmit` held real errors. Story 1.6c introduced seven; story 1.6d
introduced two more. Both were caught only because `tsc` was run by hand.

**2. Fixes were the highest-risk diffs, repeatedly.** On story 1.5d, review rounds 2 and 3 produced
eight findings and *every one* was in a fix from a previous round. On 1.6d, the helper written to
bound a query burst contained the next defect. This is now written into the review gate, but it was
learned the expensive way.

**3. Test-first slipped twice, and both are recorded.** `resolution-message.ts` was written before its
test, so no red was ever observed; it was verified afterwards by mutation, which is evidence but not
the same thing. A task's checkboxes were also ticked once before its gates ran, and unticked.

**4. Two dismissals that were wrong.** In story 1.6b a guard was twice dismissed as unreachable and
was twice reachable — `acceptance.ts` scans only the first 8192 bytes. "That input cannot get here"
is now treated as a prompt to measure rather than a conclusion.

## The finding that was reverted

Worth its own section, because it is the pattern working in the harder direction.

During story 1.6d the fix-diff gate reported that workers failing after the first would leave
unhandled rejections, and proposed a guard. The guard was added, then the sensitivity check was run:
**removing it changed nothing, because the test written for it could not fail.** `Promise.all`
attaches a handler to every promise it is given, so a later rejection is handled — merely not
reported. Both the guard and its test were removed.

A guard no test can force is exactly what the TDD rules forbid. Keeping it because a reviewer
proposed it would have been the same mistake with better manners.

### Decision recorded: no `tsc --noEmit` CI gate

**Decided by Matt at this retro:** keep the type check a local habit rather than a CI gate.

**The risk, stated plainly:** the record shows it was missed for three consecutive stories precisely
*while* it was a habit, and lint and build were green each time. If a fourth story introduces type
errors that reach `main`, this decision is the reason and it should be revisited rather than treated
as settled.

**Mitigation applied:** the habit is written into `bmad-ship-story`'s Project facts, where the other
gate rules live, so it does not depend on memory alone.

## Team agreements carried into Epic 2

1. **Two instruments, always.** A sensitivity check and an adversarial review on every diff that
   reaches `main`. Neither substitutes for the other, and epic 1 has the evidence: 29 mutations on
   story 1.5d detected 28 and still missed four defects that review found.
2. **Allow-lists, not deny-lists.** A list of what is forbidden passes everything nobody thought to
   list. This failed twice in epic 1 — once in CI, once in a port test.
3. **"That cannot happen" means measure it.** Twice wrong in one story.
4. **A fix is the highest-risk diff in a story, not the lowest.**
5. **Check what lost cover.** Re-specifying a test can delete the only assertion on a behaviour that
   is still correct, and the suite gets greener, so nothing complains.
